# Statistics page and activity heatmap (design, 2026-11-12)

## Intent

Add a core **Statistics** page that answers "how much did I consume, how highly
did I rate it, and what did I finish in this period" across every enabled media
kind, with filters for the media type, the period, genres, tags, status and the
kind's filterable fields.

The page is a **core** page, not a media plugin. The plugin contract stays
data-only (no plugin HTML/JS and no page capability); a kind declares how its
entries become statistics as plain data. That keeps the page media-agnostic and
the future marketplace path intact.

Period statistics are **completion-based** (the owner's choice): a range selects
entries by their finished date and totals use the values stored on those entries
today. A separate **activity log** is introduced for a GitHub-style heatmap of
what was actually changed day by day. It starts with this release; there is no
historical backfill.

## Goals

- A `/stats` page with a sidebar entry, available for every enabled kind.
- Summary totals and averages: entries, completed, time, units and ratings.
- Period filter: All time, This year, Last 12 months, or a custom range,
  applied to the entry's finished date.
- Filters: media type, genre, tag, status, and the selected kind's `Filterable`
  fields; all bookmarkable GET parameters.
- Per-kind comparison and per-dimension breakdowns (genre, tag and the kind's
  filterable metadata).
- One server-rendered SVG time chart, rating distribution bars, and an SVG
  activity heatmap for the last 12 months.
- A data-only `StatsDef` on `KindDef` describing how a kind derives time and
  units.
- Anime episode duration from AniList, so anime watchtime becomes computable.
- A per-item **Update from source** action that fills only missing fields, so
  existing anime items can get duration on demand without a batch backfill.
- An `entry_events` log (migration 00017) recording manual entry changes; it
  powers the heatmap and is included in backups.
- Docs, tests, preview verification.

## Non-goals

- True per-period consumption for historical data. Only changes recorded after
  this release have event history.
- Backfilling events from imports, existing `updated_at`, or finished dates.
- Counting imports or backup restores as user activity on the heatmap.
- A plugin that renders its own statistics page or HTML/JS.
- Per-session game tracking, achievements, or external playtime history.
- A timezone setting: activity days are UTC calendar days, like every stored
  timestamp.
- Aggregating credits/people (authors are already filterable fields in the
  book and manga kinds; no separate people dimension).
- Fixing the books Book/Series double-count model. The Series kind declares no
  `Stats` until that refactor, so it contributes entry counts and ratings but
  no pages/chapters.
- Automatic or batch metadata backfill. The per-item Update from source action
  is the chosen path; there is no startup sweep or bulk refresh.
- Charts that need JavaScript or a new dependency.

## Approaches considered

### Period semantics

- **A. Completion-based (chosen).** A range selects by `finished_on`; totals use
  the current values. Works for all existing data. "2026 playtime" means the
  lifetime playtime of games finished in 2026, which the page labels clearly.
- **B. Event log only.** True deltas inside a range ("hours watched in
  October"), but no history before the release and no historical stats at all.
  Rejected as the only model.
- **C. Hybrid (chosen).** A for the tables and charts; B for the heatmap. The
  activity log is general enough to support future activity metrics, but the
  first UI uses it only for the heatmap.

### Page shape

- **1. Tables and CSS bars.** Lightest, but dynamic bar widths need either
  inline styles (forbidden by the theme guard) or coarse bucket classes.
- **2. SVG dashboard.** The same data plus server-rendered SVG charts. More
  template and test work.
- **3. Hybrid (chosen).** Summary cards, tables with small SVG bars, one
  monthly/yearly SVG time chart, and an SVG heatmap. No JavaScript, no inline
  styles, theme-token colours.

### Where the statistics live

- **Core page + data-only `StatsDef` (chosen).** The page reads manifests and
  the library; plugins describe time/unit semantics as data.
- **A statistics plugin.** Would require a page capability in the contract,
  contradicting the data-only rule and the marketplace goal. Rejected.
- **Hard-coded per-kind logic in the page.** Would put media knowledge in the
  core and fail the guard. Rejected.

## Constraints

- No new Go dependencies. Charts are HTML/SVG generated by `html/template`.
- No inline scripts (strict CSP must stay possible) and no inline styles. SVG
  dimensions, positions and opacities are attributes, not CSS.
- Templates use only colour classes in `internal/appearance/tailwind-map.json`.
  SVG shapes use `fill="currentColor"` with an allowed `text-*` class.
- The core guard stays clean: no media-specific words in core Go/HTML/templates.
  Per-kind labels ("Watchtime", "Playtime", "Episodes", ...) live in plugin
  manifests.
- Contract types stay serialisable data; the JSON round trip covers `StatsDef`;
  the contract version stays 1.
- Migrations are strictly increasing. **00008 stays unused; the next number is
  00017.**
- README stays at or below 150 lines.
- The owner's existing data is not modified by the migration; stats work
  immediately for completion-based tables, and the heatmap starts empty.
- Preview only on port 18083 / project `allister-preview`; the owner's
  18080-18082 containers stay untouched. The owner pushes.

## Period and value semantics

- A period selects entries whose `finished_on` is a calendar day inside the
  inclusive range. Entries with no `finished_on` are excluded from a period and
  only appear under All time. The page says this next to the period filter.
- All time applies no date filter and includes every entry with the selected
  status and metadata filters, whether it has a finished date or not.
- `Completed` counts entries whose status is `completed`, not "has a finished
  date". A period's completed count is therefore the intersection of both.
- Ratings use the current rating. `NULL` (unrated) is excluded from averages;
  an explicit `0` is a real rating and included. The rating distribution has
  rows 0-10 plus an "Unrated" count.
- Time is stored internally in seconds and shown as `h m` (for example
  `12h 30m`). Units are the kind's primary consumed-unit count (pages,
  chapters, episodes).
- Average time is total time divided by the number of entries with recorded
  time above zero; average units uses entries with units above zero; average
  rating uses rated entries. Each card shows the contributing count so the
  denominator is visible.
- Time and unit values come only from **active** progress keys. Stored values
  of inactive keys are not counted.
- If a completed entry has an active units track at zero and a bounded total
  field exists, the total is used as the unit count (for example a show marked
  watched without episode progress). This fallback applies only to units, not
  to duration tracks.
- Entries without enough data to compute a declared time metric are counted in
  "missing time" and excluded from time totals and averages, never treated as
  zero.

## Contract: `StatsDef`

`plugin.KindDef` gains an optional pointer:

```go
// Stats describes how a kind's entries become statistics. It is optional: a
// kind without it still contributes entry counts, statuses and ratings.
Stats *StatsDef `json:"stats,omitempty"`

type StatsDef struct {
    Time  *StatsTimeDef  `json:"time,omitempty"`
    Units *StatsUnitsDef `json:"units,omitempty"`
}

// StatsTimeDef derives consumption time. At least one of DurationKey,
// CompletedField, or the UnitsKey+PerUnitField pair must be set.
type StatsTimeDef struct {
    Label          string `json:"label"`                     // "Watchtime", "Playtime"
    DurationKey    string `json:"duration_key,omitempty"`    // duration progress, seconds
    CompletedField string `json:"completed_field,omitempty"` // number field, minutes
    UnitsKey       string `json:"units_key,omitempty"`       // count/pages progress
    PerUnitField   string `json:"per_unit_field,omitempty"`  // number field, minutes
}

// StatsUnitsDef names the primary consumption count of a kind.
type StatsUnitsDef struct {
    Key         string `json:"key"`          // count/pages progress
    LabelPlural string `json:"label_plural"` // "Pages", "Chapters", "Episodes"
}
```

Validation (`internal/plugin/validate.go`, inside `validateKind`):

- `Stats` may be nil. When set, at least one of `Time` and `Units` must be set.
- `Time.Label` is required, a single line without control characters, at most
  40 runes.
- At least one time source is required. `UnitsKey` and `PerUnitField` must be
  set together.
- `DurationKey` must name an eligible progress of type `duration`.
- `UnitsKey` must name an eligible progress of type `count` or `pages`.
- `CompletedField` and `PerUnitField` must name a kind field of type `number`.
  Their values are minutes.
- `Units.Key` is required and must name an eligible progress of type `count` or
  `pages`; `Units.LabelPlural` is required, single line, at most 40 runes.
- No two `Stats` labels need to be distinct; they are display text.
- The full-manifest JSON round trip includes a `StatsDef` with every field.

Time resolution order (documented and covered by tests):

1. If the entry is completed and `CompletedField` has a positive value, use
   `CompletedField × 60` seconds.
2. Else if `DurationKey` is active, use its value in seconds (a movie position
   is capped at the runtime when both are known).
3. Else if `UnitsKey` is active and `PerUnitField` is positive, use
   `units × PerUnitField × 60` seconds, with the completed-total fallback for
   units.
4. Else the time is unknown.

This covers all built-in shapes without hard-coding kind ids in the core.

## Anime episode duration

The shared AniList client (`internal/plugins/anilist`) gains `duration` on its
search and detail selections and a `Duration *int` on `SearchResult`.

The anime kind gains:

```go
{Key: "duration", Label: "Episode duration", Type: plugin.FieldNumber,
    Unit: "min", Min: num(1), Max: num(10000), Show: true, Editable: true}
```

The anime mapping adds `duration` to the summary fields for both search and
details, guarded to 1-10000. AniList returns minutes per episode; `null` leaves
the field absent.

Stats use `episode` progress × `duration`. New items get the field from search
and details. An existing item gets it from the item page's **Update from
source** action (below); there is no automatic or batch backfill, and a manual
edit can still set it. Until an item has the field, it counts as "missing
time" when episodes have been watched. The TV runtime field also gains
`Unit: "min"` so every per-unit time field states its unit.

### Item metadata refresh (per item)

A saved item with a non-manual source gets an **Update from source** form on its
overview, next to Edit details. It is generic for every plugin and kind.

- Route: `POST /{plugin}/{source}/{id}/refresh` in `coreRoutes`.
- The handler resolves the saved item and its source, calls
  `Source.Details(ctx, kind, sourceID)` once, and passes the returned fields to
  `library.FillMissingFields`.
- Merge policy: **only fields that are absent or have no stored value are
  added.** A field that already has a value is never overwritten, so manual
  edits, imported data and earlier refreshes are safe. Titles, terms, cover,
  credits, external ids, relations, the list entry and progress are untouched.
- The source must be declared and implemented; a manual item, an undeclared
  source or an unsaved item has no action (404 on a forged POST).
- Source errors use the existing `itemFail` mapping: `ErrNotFound` 404,
  `ErrNotConfigured` 503 with the Settings hint, `ErrBadResponse` 502,
  `ErrRateLimited`/`ErrUnavailable` 503 with retry. The source's error is
  logged without credentials, as elsewhere.
- Success redirects to the item overview with `?updated=N`, which renders
  "N field(s) added from <Source>." or "Nothing new; every source field is
  already filled." The count is informational and does not affect the page.
- The action is one source call per click. It is the manual replacement for a
  batch backfill; the stats page's missing-time note points the user at it.
- `library.FillMissingFields(ctx, itemID, fields) (added []string, err error)`
  validates the fields with the same rules as `UpdateDetails` (types, bounds,
  enums, text hygiene, URLs), inserts only missing keys, and bumps the item's
  `updated_at` when it added something. It returns the added keys for the
  notice.

## Event log

### Schema (migration 00017)

```sql
CREATE TABLE entry_events (
    id INTEGER PRIMARY KEY,
    item_id INTEGER NOT NULL REFERENCES items(id) ON DELETE CASCADE,
    occurred_at TEXT NOT NULL,                -- UTC, YYYY-MM-DDTHH:MM:SSZ
    event_type TEXT NOT NULL,                 -- progress | status | rating
    progress_key TEXT NOT NULL DEFAULT '',
    old_num REAL,                             -- progress or rating; NULL = unrated/absent
    new_num REAL,
    old_text TEXT NOT NULL DEFAULT '',        -- status
    new_text TEXT NOT NULL DEFAULT '',
    origin TEXT NOT NULL DEFAULT 'manual'     -- manual | import | restore
);
CREATE INDEX entry_events_item ON entry_events(item_id);
CREATE INDEX entry_events_time ON entry_events(origin, occurred_at);
```

The table is append-only. Events are written in the same transaction as the
entry change, so a failed save writes neither.

### What is recorded

- `progress`: one row per progress key present in the save whose value changed.
  The old value is the stored value, or 0 when the key was absent. Decreases and
  clear-to-zero are recorded; the heatmap only counts increases.
- `status`: one row when the status changes, with old/new status text.
- `rating`: one row when the rating changes, with NULL for unrated and 0 as a
  real value.
- `Increment` (`+1`) records the progress delta and a status change from
  planned to active when it happens. A no-op at a total writes nothing.
- `ApplyImport` records with origin `import`; the heatmap excludes it.
- New entries (manual add, initial import, restore) are **baselines**: they
  write no events. Restored events come from the backup itself.
- Removing an entry, changing the active progress combination, or clearing
  progress writes no event.
- The library API gets an optional origin on `UpsertEntry` for imports. The
  default is `manual`; `ApplyImport` passes `import`.

### Heatmap definition

- Window: the last 12 months including today, independent of the page's period
  filter. The media filter applies; genre, tag, status and period filters do
  not.
- A **consumption event** is a progress increase (`new_num > old_num`) or a
  status transition to `completed` (`new_text = 'completed'` and the old status
  differs).
- Cell intensity is the number of consumption events with origin `manual` on
  that UTC day. A save that raises three progress keys contributes three
  events; a completion adds one more. The page calls them "activity events",
  not hours.
- Tooltips are native `<title>` text: `2026-11-12: 3 activity events`.
- "Tracked since" is the earliest manual event day, or a "starts with your next
  change" message when there are none.

### Backup and restore

`BackupEntry` gains `Events []BackupEvent` (`json:"events,omitempty"`) and
`EventsTruncated bool` (`json:"events_truncated,omitempty"`), and
`BackupItems` loads events per batch. `BackupEvent` carries the timestamp,
type, progress key, old/new numeric and text values, and origin. Restore
validates them (type, origin, RFC 3339 timestamp, eligible progress key, finite
numbers) and inserts them with the new item. The backup format version stays 1:
the fields are optional and additive.

The backup writer keeps the **newest 5,000 events per entry** and sets
`EventsTruncated` when older ones are dropped. The full log in the database is
unaffected. This keeps one item's JSON well under the backup restore limit
(`MaxItemBytes`, 4 MiB by default) and means a backup this version writes can
always be restored by this version. The restore result notes truncation.

Restore still skips an item whose identity already exists, so events are only
restored with newly created items. This is documented; merging event history
into an existing item is out of scope.

## Library additions

- `StatsRows(ctx, q, lang) ([]Row, error)` returns every entry matching the
  query without pagination, for aggregation. It is capped at 20,000 rows and
  returns `ErrTooManyRows` above that so a typo cannot exhaust memory. It
  reuses the existing row loader (fields, terms and progress are needed;
  titles are loaded by the same path and ignored).
- `ActivityDays(ctx, from, to, scope []KindRef) (map[string]int, error)` returns
  manual consumption-event counts by UTC day for the heatmap. The handler
  passes the enabled kind scope, so disabled plugins are excluded.
- `FirstActivityDay(ctx) (string, bool, error)` returns the earliest manual
  event day.
- `UpsertEntry` gains variadic `EntryOption`s; `WithEventOrigin(origin)` is the
  only option. `ApplyImport` passes `OriginImport`.
- `FillMissingFields(ctx, itemID, fields)` adds only field keys the item does
  not already have, validates them like `UpdateDetails`, and bumps the item's
  `updated_at` only when it added something.
- Event reads and writes live in a new `internal/library/events.go`.

The library stays media-agnostic: it stores rows and counts; all time/unit
interpretation comes from the manifest's `StatsDef`.

## Statistics computation (`internal/stats`)

A new package takes the rows and kind definitions and produces a report. It
imports `internal/library` and `internal/plugin`; it does not import any plugin
package.

```go
type Input struct {
    PluginID string
    Kind     plugin.KindDef
    Rows     []library.Row
}

type Options struct {
    From, To *time.Time // inclusive calendar days; nil = open
    Bucket   Bucket     // month or year
}

type Report struct {
    Kinds  []KindReport
    All    Totals
    Months []Bucket
    Genres []Dimension
    Tags   []Dimension
}
```

- `KindReport` holds the kind's `Totals`, month/year `Buckets`, and
  `Dimensions` (genres, tags and every `Filterable` field of the kind).
- `Totals` holds entries, completed, status counts, rated count, rating sum
  and average, the 0-10 distribution, time seconds, time-contributing count,
  missing-time count, units, unit-contributing count, undated-completed count,
  and the time/unit labels.
- `Bucket` is a month (`2006-01`) or year (`2006`) label plus seconds.
  Buckets are continuous between the range ends (or the min/max finished dates
  for All time); empty buckets are kept so the chart has a time axis. A custom
  range with one open end uses the earliest/latest finished date of the
  selected rows on the open side; All time always uses yearly buckets. Entries
  without a finished date contribute to totals but not to any bucket, and the
  page notes how many there are.
- `Dimension` holds a value, entries, time seconds, units, rated count and
  rating sum. Genres and tags merge case-insensitively across kinds for the
  All-media view; the first display spelling wins. Duplicate values on one
  entry count once.
- Dimensions use text, enum, list and number fields. Date fields are filters,
  not dimensions (too many distinct values). Number values are rendered
  without a decimal point when whole. Text values are used verbatim: a
  comma-joined value such as a platform list is one dimension value.
- The All-media totals sum entries, completed, rated counts, rating sums and
  time. Units are **not** summed across kinds (pages, chapters and episodes are
  not comparable); the per-kind table shows them separately.
- Rows are filtered by `finished_on` in `Build`; all other filters are applied
  by the library query before the rows arrive.
- The Series kind has no `StatsDef`, so its units/time are zero but its entry
  counts and ratings still aggregate.

## Web page

### Route and navigation

- `GET /stats` is added in `internal/web/server.go`.
- `POST /{plugin}/{source}/{id}/refresh` is added to `coreRoutes` for the
  per-item Update from source action (above).
- The sidebar gets a core "Statistics" row (`/stats`, icon `bar_chart`) next to
  Calendar and Settings. It is active on `/stats` and its subpaths (there are
  none yet).
- The page is available even with no plugins; it shows an empty state.

### URL parameters

- `media`: empty or `all` for every enabled kind, else `<plugin>/<kind>`
  (a bare `<plugin>` is accepted when it has exactly one kind).
- `period`: `all` (default), `year`, `12m`, `custom`.
- `from`, `to`: `YYYY-MM-DD`, used with `custom`; either may be empty for an
  open end. A present `from`/`to` implies `custom` when `period` is absent.
  `from > to` is refused with a notice.
- `status`: a core status class.
- `genre` (repeatable) with `genre_mode=any|all`; `tag` likewise with
  `tag_mode`.
- `f.<field>`: the selected kind's filterable fields, with the same syntax as
  the list (`a..b`, `a..`, `..b` or one value for number/date; one value for
  enum/list; substring for text).
- Unknown or invalid parameters are ignored and named in a notice, like the
  list. `f.*` is ignored when the media filter is All.
- No `q`, sort, progress-state or rating-range filters in this version.

`year` means the current calendar year (Jan 1-Dec 31). `12m` means the 12
calendar months ending with the current month (the first day of the month 11
months ago through the last day of the current month). The server clock is the
injected `now`; days are UTC.

### Layout

1. Header with the page title and a short explanation of the completion-based
   period.
2. Filter card: media select, period select with custom date inputs, status
   select (the kind's status labels, or neutral core labels for All media),
   genre/tag multi-selects with counts, the selected kind's filterable fields,
   Apply and Clear. A plain GET form; no htmx.
3. Notices: ignored parameters, too many rows, entries missing time data,
   completed entries without a finished date when a period is active.
4. Summary cards: entries, completed (with completion rate), total time,
   average time, total units (kind view), average units (kind view), average
   rating, rated/unrated counts. The All-media view omits unit cards.
5. Per-kind comparison table (All media only): kind, entries, completed, time,
   average time, units, average rating; the kind name links to its media
   filter.
6. Time chart: one SVG bar chart for the selected scope, monthly for year/12m
   and custom ranges up to 24 months, yearly otherwise. The figure carries a
   title, description and a `<details>` table of the values. Bars use
   `fill="currentColor"` under an allowed `text-indigo-400` class. The chart
   is hidden when the scope has no time metric or every bucket is zero.
7. Rating distribution: a table of 0-10 plus unrated, each with a small SVG bar
   and count.
8. Dimension tables: genres, tags, then every filterable field of the selected
   kind (All media: genres and tags only). Each shows the top 10 values with
   entries, time, units and average rating where applicable, and a `<details>`
   "Show all" for the rest.
9. Activity heatmap: last 12 months, one SVG cell per UTC day, Monday-first
   weeks, month and weekday labels, five intensity levels, a legend, and a
   "Tracked since" line. The SVG carries a `<title>` per cell and a visually
   hidden table of active days.
10. Empty states for no plugins, no entries, no rows matching filters, no time
    data and no activity.

### Visual and technical rules

- Cards, tables and form controls follow the existing list/settings styling:
  `rounded-lg border border-slate-800 bg-slate-900`, muted labels, strong
  values.
- No `style` attributes. SVG shapes use `x`, `y`, `width`, `height`,
  `fill-opacity`, `rx` and `<title>`; no CSS bars with dynamic widths.
- Only mapped colour classes: `text-indigo-400` for chart/heatmap marks,
  `text-slate-400`/`text-slate-500` for labels and empty cells,
  `text-emerald-400`/`text-amber-300`/`text-red-300` if status colours are
  reused.
- The page is server-rendered; no new JavaScript. The existing `app.js` is
  untouched.
- The filter form preserves values on reload and offers a Clear link back to
  `/stats`.

## Decisions left to the builder

- Exact card order and wording; the page title is "Statistics".
- Chart viewBox dimensions, bar radius, label density and heatmap cell size.
- Whether multiple time sources resolve in the documented order or a future
  contract version adds an explicit unit; this version uses minutes for fields
  and seconds for duration progress.
- `StatsRows` cap (20,000) and the backup event cap (the newest 5,000 per
  entry, with the truncation flag).
- Whether to show every filterable field dimension at once or behind one
  "More breakdowns" disclosure; the data is available either way.
