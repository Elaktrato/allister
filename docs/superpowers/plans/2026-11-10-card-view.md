# Card View Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Session state:** completed 2026-11-10 — merged to `main` (`feat/card-view`), the card templates use only the appearance-mapped colours (solid translucent overlay instead of a gradient; the completed/dropped corner shades map to the `success`/`danger` tokens).

**Goal:** A card view of the core list (cover, title overlay, usable +1, status corner) that the plugin home opens by default, with per-plugin home settings.

**Architecture:** The view rides the existing list (`view=cards|table`, default from `plugin.<id>.home.view`); a new cards partial renders in the rows region; the +1 posts the same route with a hidden `view=cards` so the response is the card. Per-plugin settings gain a home form.

**Tech Stack:** Go (internal/web), html/template + htmx, Tailwind standalone (classes must be literal in templates — its content glob is templates-only).

**Spec:** `docs/superpowers/specs/2026-11-10-card-view-design.md`

## Global Constraints

- No media words in core code/templates (`internal/guard`); progress wording comes from the kind manifest.
- htmx contract unchanged: `#list-rows` swaps, `hx-history="false"`, Vary header, out-of-band swaps never touch focused inputs; no inline scripts (app.js only).
- Settings keys are flat: `plugin.<id>.home.view`, `plugin.<id>.home.statuses`.
- Every list URL stays bookmarkable; `status=all` always means all statuses.
- Full suite, `vet`, `fmt` pristine before each commit; TDD (red first).
